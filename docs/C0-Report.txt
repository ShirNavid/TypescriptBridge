SCENARIO A1 — PLAIN C# F5
================================================================================

Question:
    Can a plain net8.0 C# executable project cause Visual Studio 2026
    to automatically attach the JavaScript debugger to an Edge process
    merely because the C# application launches Edge?

Setup:
    - C0Host.csproj: net8.0, OutputType=Exe
    - Program.cs: HttpListener on 127.0.0.1:51111, launches Edge with
      --remote-debugging-port=9222
    - wwwroot/index.html + app.js + app.js.map (linked source map)
    - app.ts available on disk
    - breakpoints set in both Program.cs and app.ts

Observed:
    - C# breakpoint:              HIT
    - Edge opened:                YES
    - Page loaded in Edge:        YES (after fixing wwwroot copy)
    - TypeScript breakpoint:      NOT hit
    - VS Debug menu after F5:     Stop Debugging active; no JS adapter
    - Debug -> Attach manually:   works, but is a manual step

Verdict:
    F5 on a plain C# executable does NOT automatically attach the
    JavaScript debugger.

    VERDICT:  UNSUPPORTED

    Note: this is consistent with the documented VS F5 model, where F5
    invokes the startup project's DebugLaunch behavior. A C# project's
    debug target is the C# debugger, not the JS debugger.

SCENARIO A2 — .esproj + LAUNCH.JSON
================================================================================

Question:
    Does the .esproj / JSPS project system provide the supported F5 →
    JavaScript debugger launch we need, while a separate C# executable
    owns the HTTP host and application lifetime?

Setup:
    - C0Host.csproj: net8.0, HttpListener on 127.0.0.1:51112, no browser launch
    - C0Web.esproj: JSPS project with StartupCommand that runs the C# host
    - C0Web\.vscode\launch.json: type=edge, url=http://127.0.0.1:51112/index.html
    - C0A2.slnx: solution containing both projects
    - breakpoints set in wwwroot\app.ts

Iterations (each validated):

    1. Initial attempt failed because the C# host crashed on
       Console.KeyAvailable when stdin was redirected by VS.
       Fix: use CancellationToken + CancelKeyPress instead.

    2. Initial attempt also failed because wwwroot was not copied to
       the output directory.
       Fix: add <None Update="wwwroot\**\*"> with CopyToOutputDirectory.

    3. Source map path was wrong: "sources": ["../app.ts"] resolved to
       a path that did not exist under webRoot.
       Fix: put app.ts next to app.js.map and use "sources": ["app.ts"].

    4. webRoot was pointing at C0Web\ and resolved app.ts to the wrong
       location.
       Fix: set webRoot to ${workspaceFolder}/../C0Host/wwwroot.

    5. Browser cache served stale app.js across F5 runs.
       Fix: use a per-test userDataDir in launch.json.

    After fixes:

    - F5 on .esproj:              starts C# host via StartupCommand
    - Edge opens:                 YES (via launch.json)
    - Page loads:                 YES
    - VS debug adapter:           ATTACHED (visible in Processes window)
    - TypeScript breakpoint:      HIT
    - Locals:                     WORKING
    - Call Stack:                 WORKING
    - F10 / F11:                  WORKING
    - F5 (Continue):              WORKING

Verdict:
    The .esproj + launch.json + C# host combination is a working
    supported architecture for the Secondary Vision.

    VERDICT:  VERIFIED

SCENARIO A2.x — LAUNCH.JSON DYNAMIC RELOAD
================================================================================

Question:
    Does VS reload launch.json on every F5, without restarting VS?

Reason for asking:
    We need per-session userDataDir and (possibly) per-session port to
    avoid cache problems. If VS caches launch.json, this is not possible.

Test:
    - Change launch.json between two F5 runs (new userDataDir).
    - Also change app.ts so we can detect a fresh build.
    - Rebuild app.js. Do NOT restart VS.
    - Press F5.

Observed:
    - Edge launched with the new userDataDir.
    - Updated app.ts content appeared in the browser console.
    - No VS restart was required.

Verdict:
    Visual Studio reads launch.json on every F5.

    VERDICT:  VERIFIED

    Architectural consequence:
    We can safely regenerate launch.json between sessions, and it will
    take effect on the next F5 without a VS restart.

================================================================================
ADDITIONAL FINDINGS
================================================================================

FINDING 1 — HttpListener is sufficient for the HTTP host

    The C# host uses System.Net.HttpListener.
    Node.js is NOT required.
    The Tool's Node-based server.js is unnecessary for the final
    architecture and will be removed in C5.5.

    VERDICT:  VERIFIED

FINDING 2 — Console.KeyAvailable throws under VS

    When the C# host is started by VS through the .esproj StartupCommand
    (or by dotnet run with piped stdin), Console.KeyAvailable throws
    InvalidOperationException and kills the process.

    Required pattern for the final Program.cs:
        use CancellationTokenSource + Console.CancelKeyPress
        use !Console.IsInputRedirected guards
        do not rely on Console.KeyAvailable as the primary lifetime signal

    VERDICT:  VERIFIED

FINDING 3 — webRoot must point to the folder containing .ts sources

    webRoot in launch.json must point to the directory that contains
    (or is the base of) the .ts sources referenced by the source map.
    If webRoot points elsewhere, breakpoints remain unbound even though
    the JS debugger is attached.

    In the final TypescriptBridge architecture, webRoot should point to
    the folder that contains ts/app.ts (or, more precisely, to the
    folder the source map resolves app.ts against).

    VERDICT:  VERIFIED

FINDING 4 — Per-session userDataDir avoids browser cache problems

    Browsers cache JavaScript aggressively. Repeated F5 cycles can serve
    stale app.js.

    Solution: pass a per-session userDataDir to the browser launch.
    VS reloads launch.json on every F5, so launch.json can carry a
    per-session path written by the pre-build target.

    VERDICT:  VERIFIED

FINDING 5 — Two projects in one solution work

    A .slnx solution containing both a C# project and an .esproj project
    loads correctly in Visual Studio 2026 and supports F5 with .esproj
    as the startup project.

    VERDICT:  VERIFIED

================================================================================
CHOSEN ARCHITECTURE FOR THE SECONDARY VISION (BASED ON C0)
================================================================================

Primary:
    .esproj (JSPS) is the startup/debug project.
    launch.json provides the browser launch and JS debugger target.
    A C# executable started by .esproj's StartupCommand owns the HTTP host
    and process lifetime.
    The C# executable does NOT launch the browser in the F5 path.

Fallback (if .esproj-only ever becomes impractical):
    Multi-startup solution with .slnLaunch.

Not chosen (recorded for historical clarity):
    - Plain C# F5 → auto-attach
      UNSUPPORTED by C0.2.
    - Custom IVsDebugger2 call from the VSIX
      No public JavaScript engine GUID; out of scope.
    - VSIX orchestration of the debugger
      Not needed because .esproj works.

================================================================================
IMPLICATIONS FOR THE SECONDARY ARCHITECTURE DOCUMENT
================================================================================

The following refinements are now facts and should be applied:

1. Program.cs MUST NOT launch the browser during F5.
   The .esproj + launch.json owns browser launch during F5.

2. Program.cs MUST use CancellationToken-based lifetime.
   Do not use Console.KeyAvailable.

3. Program.cs MUST ensure app.ts and app.js.map coexist under the
   folder that webRoot points to.

4. launch.json is regenerated (or overwritten) per session by an
   MSBuild pre-build target in the .esproj.

5. The per-session userDataDir in launch.json is REQUIRED for reliable
   debugging across successive F5 runs.

6. webRoot MUST point to the folder containing app.ts as seen by the
   source map, not to the .vscode folder and not to the project root.

7. server.js (Node) is obsolete for the final runtime. Removal is
   scheduled as C5.5.

8. HttpListener-based HTTP host is the authoritative runtime HTTP.

9. Chrome and Edge are both supported, using the same architecture,
   with only a different launch.json "type".

10. The pinned Microsoft.VisualStudio.JavaScript.Sdk version
    (currently 1.0.6165494) is a NuGet pin, not a machine-specific
    VS folder reference. It should be updated only as a controlled
    compatibility change.

    .esproj + launch.json

    - a custom debugger
    - a VSIX debug engine
    - Node.js
    - modifying Visual Studio itself
